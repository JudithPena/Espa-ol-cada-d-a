# Схема и педагогический линтер отдельного курса грамматики

Документ для авторов юнитов и ревьюеров. Это проверка **самостоятельного курса грамматики**, не основного курса A0–C2 и не разбора книг.

## Запуск

```bash
python -m pip install -r requirements.txt
python -m espanol grammar-lint
python -m espanol grammar-lint 5
python -m espanol grammar-lint --report docs/grammar_audit/LINTER_BASELINE.md --json-out /tmp/grammar-findings.json
python -m espanol grammar-lint 48 --strict-warnings
python tools/grammar_schema_docs.py
python -m pytest -q tests/test_grammar_quality.py
```

`grammar-lint` возвращает ненулевой код при новых структурных `ERROR`. Педагогические `WARNING` и `INFO` **не блокируют сборку**, кроме добровольного режима автора `--strict-warnings`. В CI сначала проверяется техническая структура, затем сохраняется полный JSON со всеми находками. Markdown-отчёт группирует проблемы по правилам и наиболее проблемным юнитам, а не выводит тысячи одинаковых строк.

В `--json-out` **каждая находка** содержит `severity`, `rule`, `unit`, `group`, `question` (номер вопроса с 1), `file`, `message`, `reason`, `recommendation`, `fingerprint`, `baseline`. Для проверки тестовых данных можно использовать `--directory PATH`. Если `unit` не указан, проверяются все файлы `content/grammar/[0-9]*.json` независимо от их количества.

## Структурные ошибки (ERROR)

| Правило | Что не так | Как исправить |
|---|---|---|
| `JSON_PARSE`, `SCHEMA` | Неразбираемый JSON, неизвестное или обязательное поле отсутствует, неверный тип, несовместимые поля | Открыть `content/grammar/schema.json` и [справочник полей](grammar_fields.md) |
| `DUPLICATE_UNIT`, `DUPLICATE_UNIT_NUMBER`, `DUPLICATE_GROUP` | Одинаковые идентификаторы или номера | Сохранять прежние идентификаторы; менять только новый конфликтующий объект |
| `MISSING_THEORY_LINK`, `BROKEN_THEORY_LINK` | Упражнение не связано с теорией или ссылки неверны | Указать существующие индексы `theorySections` |
| `BROKEN_LEARNING_ORDER` | Пропуск, повтор или лишний маршрутный этап | Синхронизировать `learningOrder` с разделами/упражнениями/итогом |
| `UNAVAILABLE_ANSWER` | В `options` нет правильного ответа | Проверить `answers`, `options`, допустимые альтернативы |
| `CONFLICTING_INPUT`, `ARTICLE_INPUT_CONFLICT`, `UNSUPPORTED_BUILD` | Несовместимая комбинация вариантов, плиток и ввода | Использовать один из поддерживаемых форматов; `guidedGaps + options` разрешён для `gap-choice` |
| `UNBUILDABLE_ANSWER` | Невозможно собрать ответ из `tiles` | Проверить количество и регистр слов, не подменяя правильный ответ |
| `GAP_ARITY`, `GUIDED_ARITY` | Количество частей, пропусков и ожидаемых слов расходится | Согласовать `gapParts`, `gapWordCounts`, `guidedGaps.parts/choices` |
| `MISSING_PICTURE`, `MISSING_IMAGE_ALT` | Нарушена структура изображения | Добавить путь `.webp` и содержательный альтернативный текст |

Схема проверяет также таблицы, иллюстрации, варианты ответа, `inputFormat`, словарные группы, схемы, `answerWarnings`, данные рисунков и структуру разделов. Уже существующие проверки в `espanol/grammar.py` **сохранены** и продолжают проверять содержательную сборку, ссылки на рисунки, нормативные варианты с предупреждением и т. п.

## Методические предупреждения (WARNING)

| Правило | Причина | Проверить вручную |
|---|---|---|
| `SHORT_CHECK` | Мини-проверка состоит лишь из 1–2 вопросов с выбором | Хватает ли проверки понимания, нужен ли короткий ввод? |
| `LONG_MODE_RUN` | Серия из восьми или более одинаковых действий | Осмысленное закрепление или механическая серия? |
| `LONG_HOMOGENEOUS` | Более 20 вопросов одного типа | Нет механического запрета на длину; проверить разнообразие случаев |
| `DOMINANT_ANSWER` | Один ответ верен не менее чем в половине из шести и более вопросов | Можно ли угадывать ответ по частоте? |
| `NEVER_CORRECT_OPTION` | Вариант встречается в пяти и более вопросах группы, но ни разу не верен | Пример: «Без артикля» в упражнении 7.1 |
| `FIXED_ANSWER_POSITION` | При явно отключённом перемешивании правильная кнопка всегда на одном месте | Действительно ли фиксированный порядок нужен? |
| `CONTEXT_LEAK`, `CONTEXT_PREDICTS_ANSWER` | Русская подсказка сообщает грамматическую категорию или однозначно коррелирует с ответом | Контрольный пример: 5.2; описать ситуацию, а не правило |
| `DIRECT_ANSWER_HINT`, `CLUE_IS_ANSWER` | Подсказка содержит готовую форму ответа | Не заменяет ли воспроизведение копированием? |
| `SUSPICIOUS_DISTRACTOR` | Встречена известная из аудита искусственная форма (`relojs`, `hotels` и т. п.) | Проверить по RAE/ASALE; эвристика **не словарь** |
| `REPEATED_EXPLANATION`, `GENERIC_EXPLANATION` | Объяснение дублируется у 4+ вопросов или слишком общее | После третьей ошибки нужен конкретный разбор проверяемого случая |
| `DUPLICATE_PROMPTS` | Три и более одинаковых формулировки внутри группы | Действительно ли меняется контекст и мыслительное действие? |
| `CHECK_THEORY_SCOPE` | Мини-проверка связана с необычной теорией | Проверить методический смысл ссылки |

Инструкции о том, как нажать «Без артикля», **не считаются раскрытием ответа**. Проверяется конкретная подсказка к вопросу. Линтер может ошибаться и не знает нормативность всех слов.

## Информация (INFO)

| Правило | Что означает |
|---|---|
| `BUILD_WITHOUT_DISTRACTORS` | Короткая сборка только из слов ответа; иногда это оправданно |
| `EMPTY_CHECK_INSTRUCTION` | У мини-проверки нет собственной инструкции |
| `POSSIBLE_UNTAUGHT_GRAMMAR` | Эвристически замечена сложная форма в раннем юните; порядок обучения проверяется вручную |
| `FILE_ID_MISMATCH` | Историческое имя файла не совпадает с `unit.id`; **не переименовывать существующие id** |
| `UNIT_FORMAT_DIVERSITY` | В юните только одна операция в упражнениях; возможна осмысленная причина |
| `INPUT_WORDING_FOR_CHOICES` | Фраза «впиши» при задании с выбором; требуется проверка текста инструкции |

## Как трактовать отчёт

Предупреждение — **основание перечитать вопрос**, не команда механически менять ответы. Сначала подтвердить проблему по исходному предложению и соответствующей теории. Затем выбрать действие: исправить формулировку в отдельной задаче на один юнит, отклонить ложный сигнал с аргументацией или оставить педагогически оправданное повторение. Не заменять корректные ответы ради статистического распределения, не вводить запрет на упражнения длиннее 15 вопросов.

**Отдельная обязательная ручная проверка:** покрытие всех правил и исключений учебника, актуальная грамматика RAE/ASALE, естественность испанского, сопоставление объяснения с конкретными допустимыми вариантами, соответствие сложности уже пройденной теории. Автоматический линтер **не подтверждает** эти пункты.

## Прозрачный учёт исторических проблем

`content/grammar/lint_allow.json` имеет два списка: `knownErrors` и `acceptedWarnings`. В каждой записи обязательны `fingerprint` из JSON-отчёта и содержательная `reason` (не менее 15 символов). Инструмент **не создаёт исключения автоматически**. Исключение не скрывает находку из отчёта: она видна с `baseline: true`. Только *документированные старые* ERROR временно не блокируют CI; любой новый ERROR блокирует. Пример:

```json
{"knownErrors": [{"fingerprint": "<из вывода --json-out>", "reason": "Старый вопрос, заведена отдельная задача на исправление, сохранить до согласования"}], "acceptedWarnings": []}
```

Сегодняшняя стартовая проверка: ноль структурных ERROR, поэтому исключений нет. Для новых юнитов следует стремиться к нулю необъяснённых WARNING. При рассмотрении warning можно записать конкретную причину в комментарий/отчёт юнита без глобального отключения правила.

## Порядок разработки нового юнита

1. Прочитать `content/grammar/AGENTS.md`, универсальный гайд и справочник полей; составить карту «теория — практика — проверяемая цель».
2. Создать JSON по формальной схеме, использовать существующие типы задания; не менять старые `unit.id`, `group.id`, позиции вопросов, `answers` и ключи прогресса.
3. Выполнить `python -m espanol grammar-lint NN --strict-warnings` и исправить реальные нарушения; сомнительные варианты проверить со словарями.
4. Выполнить `python -m espanol validate`, `python -m pytest -q`, тесты грамматики Node.js, затем браузерное тестирование по 320/390 px с настоящими ответами и тремя ошибками.
5. Сверить теорию и каждый ответ вручную; зафиксировать результаты и оставшиеся риски в отчёте юнита. Не переходить к следующему автоматически.

## Добавление типа упражнений

Новый формат нельзя ввести только полем JSON. Сначала отдельный PR: движок (`gQuestionMode`, отображение, ввод, обратная связь), оценивание, JSON Schema и генерация справочника, регрессии с ошибками/жизнями/вариантами, браузерные сценарии. Не подменять этим этапом изменение механики трёх жизней или проверки ударений.
