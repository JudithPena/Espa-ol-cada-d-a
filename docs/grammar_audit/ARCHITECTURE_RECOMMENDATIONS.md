# Архитектура раздела «Грамматика»: рекомендации

Основание — [отчёт аудита](AUDIT_REPORT.md) (идентификаторы находок вида E-02, A-01 — оттуда).
Порядок и объём работ — в [плане](IMPLEMENTATION_ROADMAP.md).

## Главная мысль

Переписывать раздел не нужно. Модель «юнит = один JSON, движок = общий плеер» правильная и уже выдержала
рост с 17 до 45 юнитов. Мешать дальнейшему росту будут четыре вещи:

1. **Формат данных нигде не описан и почти не проверяется.** Каждый новый автор (человек или модель)
   выводит его из соседних файлов.
2. **Оценивание зависит от текста и догадок**, а не от данных: ударения, пунктуация, тип вопроса,
   «мини-проверка».
3. **Всё лежит в одной странице**: 45 юнитов сегодня — 8 МБ, 150 юнитов — около 12–13 МБ только текста.
4. **Качество содержания не проверяется автоматически**, поэтому одни и те же дефекты повторяются
   из юнита в юнит.

Ниже — семь рекомендаций в порядке пользы. Для каждой указано, что остаётся совместимым.

Общее правило совместимости для всех пунктов: **не менять `unit.id`, `group.id`, порядок вопросов
в группе и строки `answers`**. На них держатся сохранённый прогресс (`P.grammar`, ключ `unit.id/group.id`),
журнал попыток и снимок `tests/data/grammar_question_signatures.json`.

## 1. Формальная схема юнита и строгий загрузчик

**Проблема.** A-01: 68 разных полей, проверяется около 15 конструкций, неизвестные ключи проходят.

**Что сделать.**

- Описать формат одним файлом `content/grammar/schema.json` (JSON Schema) и проверять им каждый юнит
  в `load_grammar()`. Содержательные проверки, которые схемой не выразить (сборка из плиток даёт ответ,
  `learningOrder` содержит каждый этап), остаются в `grammar.py`.
- Включить `additionalProperties: false`: опечатка в имени поля станет ошибкой сборки.
- Добавить проверки, которых сейчас нет: `number`, `level`, `title` юнита; непустая `instruction`
  у мини-проверки (сейчас пустая у 65); обязательный `theorySections` у упражнения (сейчас при отсутствии
  молча берётся раздел 0, N-04); совпадение имени файла с `id` — как предупреждение для старых 12 файлов.
- Из той же схемы генерировать короткий справочник полей `docs/grammar_fields.md`. Тогда документация
  не сможет разойтись с кодом (находка G-02).

**Зачем.** Это самый дешёвый способ, чтобы Codex, Sonnet и Opus писали юниты одинаково: схема отвечает
на вопрос «какие поля бывают и в каких сочетаниях» точнее любого текста.

**Совместимость.** Данные не меняются. Схему сначала пишем по фактическим данным, затем ужесточаем.

## 2. Явный тип вопроса вместо угадывания

**Проблема.** Режим вычисляется по набору полей (`gQuestionMode`, `grammar_player.js:474–479`);
у 1437 вопросов из 2020 поле `interaction` отсутствует. Мини-проверка определяется по заголовку (N-01).

**Что сделать.**

- Ввести обязательное поле `type` у вопроса с закрытым списком значений:
  `choice`, `input`, `gaps-input`, `gaps-choice`, `build`. Для старых данных загрузчик выводит его
  по нынешним правилам и записывает в загруженную структуру; новые юниты обязаны указывать явно.
- Ввести у группы `kind: "check" | "exercise"` (загрузчик проставляет сам: группа из `section.check` —
  это `check`). Все сравнения со строкой «Мини-проверка» заменить на `kind`.
- В движке завести таблицу типов: для каждого `type` — три функции: отрисовать, собрать ответ, показать
  разбор. Новый формат — новая строка таблицы, а не правка большой функции `gPlayerView`.

**Зачем.** Сейчас добавление формата — правка строк по 1000 знаков в трёх местах. С таблицей типов
появляется место для сопоставления пар и распределения по группам (см. п. 6), и их можно тестировать отдельно.

**Совместимость.** Сохранённые ответы не затрагиваются: меняется только способ выбора отрисовки.

## 3. Оценивание по данным: ударения, пунктуация, пропуски

Все три изменения делаются в одной функции `grammarResult` (`site_template.html:2353–2374`) и её данных.

### 3.1. Ударения (E-02)

- Убрать поиск слова «ударение» в тексте задания и список `G_ACCENT_MEANING` как источник решения.
- Ввести явное поле `accents` у группы и у вопроса (вопрос важнее группы):
  `"strict"` — пропущенное ударение = ошибка; `"lenient"` — жёлтый ответ.
- Значение по умолчанию задаётся на уровне юнита (`accentsDefault`). Для юнитов о глагольных формах,
  вопросительных словах и самом ударении — `strict`.
- Страховка в загрузчике: если ответ без ударения совпадает с другим существующим словом из небольшого
  встроенного списка пар (`tu / tú`, `el / él`, `esta / está`, `hablo / habló`…) или с другим ответом
  этого же юнита, а режим `lenient`, — ошибка сборки. Так список слов остаётся, но как проверка автора,
  а не как логика оценивания.
- Перенос: для существующих юнитов проставить значения так, чтобы поведение не изменилось, затем
  осознанно исправить несогласованные места (43.x: `están`, `estáis`; 39.4; 45.x: `tenéis`).

### 3.2. Пунктуация (E-05)

- Ввести `normalize: "phrase"` для ответов-предложений: перед сравнением убирать `¿ ? ¡ ! . , ; :`
  и лишние пробелы. Для коротких форм оставить нынешнее сравнение.
- После этого 86 вопросов с перечисленными вариантами можно упростить до содержательных ответов.
  Старые записи оставить в `answers` как есть — они просто станут избыточными.

### 3.3. Несколько пропусков (E-03)

- Хранить ответы по пропускам: `gapAnswers: [["le"], ["se"], ["la"], ["se"], ["la"]]` — список допустимых
  значений для каждого поля. Строка `answers` остаётся для совместимости и снимков; загрузчик проверяет,
  что `gapAnswers` порождает те же полные ответы.
- В разборе подсвечивать неверные поля и показывать верное значение рядом с каждым, а не строку
  `le se la se la`.
- Жёлтые варианты привязывать к конкретному пропуску.
- Решение автора: списывать одну жизнь за вопрос (как сейчас) или за каждое неверное поле. Рекомендую
  оставить одну за вопрос — это не меняет лимиты.

### 3.4. Лимит ошибок (E-01)

- Оставить формулу `max(3, ceil(n / 5))`, но текст вступления строить из неё: «После N ошибок…».
- Либо разрешить явное поле `lives` у упражнения и убрать формулу. В любом случае число на экране
  и в инструкциях должно браться из одного места.

**Совместимость.** Сохранённые ответы — строки; они продолжают оцениваться. Ужесточение ударений может
сделать старый «жёлтый» ответ красным при повторном открытии. Чтобы не ухудшать лучший результат,
`P.grammar` не пересчитываем (так и сейчас: хранится только число верных).

## 4. Загрузка юнитов по требованию

**Проблема.** A-03: страница 8,2 МБ (4,2 МБ в gzip); все юниты и картинки заданий встроены.

**Что сделать.** Повторить уже работающее решение для картинок теории (`write_theory_illustrations`,
файлы `g/<хеш>.webp`):

- В страницу встраивать только каталог: `id`, `number`, `title`, `subtitle`, `level`, `icon` и список
  этапов маршрута с ключами групп (он нужен для отметок «пройдено» и замков).
- Тело юнита писать в `g/u/<id>.<хеш>.json`; плеер загружает его при открытии юнита и показывает
  короткое «Загружаю урок…».
- Картинки заданий и портреты тоже выносить в файлы `g/`.
- Режим `--fragment` оставить со встраиванием — для переносимой одиночной страницы и для тестов в `vm`.

**Что это даёт.** Страница уменьшится примерно на 1,4 МБ текста грамматики плюс её картинки; рост курса
перестанет влиять на время входа. Заодно `P.grammar` перестанет зависеть от наличия всех данных в памяти.

**На что обратить внимание.**

- Экран завершения показывает следующий юнит — данные для него есть в каталоге.
- Сейчас сайт открывается и работает без сети после первой загрузки одной страницы. С отдельными
  файлами офлайн-работа потребует кэширования (service worker). Это решение автора: нужен ли офлайн.

**Совместимость.** Ключи прогресса не меняются. Тесты в `vm` продолжают работать через `--fragment`.

## 5. Хранение попыток

**Проблема.** N-05: журнал попыток растёт без очистки и переписывается на каждую букву; ошибка записи
молча проглатывается.

**Что сделать.**

- Хранить попытку отдельным ключом на группу (`grammar-attempt.v2/<unit>/<group>`), а не одним объектом
  на весь курс. Запись на нажатие клавиши станет записью одной маленькой строки.
- Для завершённой попытки (`passed`) оставлять только то, что нужно для «Повторить ошибки», либо удалять
  её при старте новой. Незавершённые хранить полностью.
- Черновик ввода сохранять с задержкой 300–500 мс, а не на каждый символ. Проверенный ответ — сразу.
- В `store.set` возвращать успех или неудачу; при неудаче один раз показать сообщение
  «Не получается сохранить прогресс: в браузере закончилось место».
- Перенос: при первом запуске разложить старый `grammar-attempts.v1` по новым ключам и удалить его.

**Совместимость.** Нужна одноразовая миграция с тестом: старый журнал с активной, проваленной
и завершённой попыткой → те же состояния после переноса.

## 6. Новые форматы — через общий движок, а не внутри юнита

**Проблема.** A-04: гайд требует сопоставление и распределение по группам; в грамматике их нет,
в основном курсе есть (`matchPick`, `sortPick`).

**Что сделать.**

- После п. 2 (таблица типов) добавить два типа: `match` (пары) и `sort` (распределить по группам).
  Логику выбора и подсчёта ошибки взять из основного курса; оценивание — через общий `grammarResult`
  по правилу гайда «одно подтверждённое неверное сопоставление = одна ошибка».
- Добавлять формат отдельной задачей с собственными тестами и только потом использовать в юнитах.
  Запретить в инструкциях дописывать движок «по пути» при создании юнита.
- Мини-проверкам разрешить те же типы, что и упражнениям: сейчас все 424 вопроса — выбор (C-01).

## 7. Тесты и автоматический контроль содержания

**Проблема.** A-06 и G-04: содержательные дефекты (C-02 – C-05, C-08, C-09) не ловятся ничем.

**Что сделать.**

1. **Линтер содержания** `python -m espanol grammar-lint [юнит]` — те же сканеры, что использованы
   в аудите, с выводом «вопрос — причина». Правила:
   - вариант предлагается в 5+ вопросах упражнения и ни разу не верен;
   - один ответ верен в половине вопросов и чаще (упражнение от 6 вопросов);
   - одна подпись `context` в 3+ вопросах всегда ведёт к одному ответу;
   - одно предложение пояснения повторяется в 4+ вопросах упражнения;
   - подпись говорит «Впиши», а вопрос — выбор;
   - ввод совпадает с подсказкой `clues`;
   - сборка без лишних плиток при длине ответа до 5 слов;
   - ответ с ударением в мягком режиме;
   - упражнение длиннее 20 вопросов; мини-проверка без инструкции.
   
   Режим: **предупреждения** с файлом исключений `content/grammar/lint_allow.json`, где у каждого
   исключения есть причина. Так сохраняется принцип гайда «без жёстких квот», но каждое отступление
   становится осознанным. Для новых юнитов — ноль необъяснённых предупреждений.
2. **Браузерный проход** `tools/grammar_walk.mjs` по образцу существующего `tools/site_walk.mjs`:
   один юнит, ширины 320 и 390, по одному вопросу каждого типа, сценарий «ошибки → теория → повтор»,
   проверка горизонтальной прокрутки и размеров целей нажатия. Запускать в CI для изменённых юнитов.
3. **Разделить `tests/site_grammar.test.cjs`** (182 КБ) по темам: оценивание, попытки и жизни,
   порядок вариантов, маршруты, проход юнитов. Общая загрузка страницы — в `tools/site_vm.cjs`,
   который уже есть.
4. **Снимки.** 30 файлов `tests/data/grammar_before_unitNN.json` заменить одним снимком подписей
   (`grammar_question_signatures.json` уже есть) с правилом: существующие ключи и ответы не исчезают,
   новые добавляются.
5. **Устаревшая форма.** Удалить `grammarForm` и `gSubmitGrammarForm` вместе с тестами, которые
   проверяют только её (A-05). Тесты, которые через неё проверяют оценивание, перевести на плеер.

## Чего делать не стоит

- **Не вводить фреймворк и сборщик.** Одностраничный сайт без зависимостей — сильная сторона проекта.
  Достаточно разнести функции отрисовки по типам и укоротить строки.
- **Не переводить юниты в YAML или в код.** JSON с проверкой схемой удобен моделям и тестам.
- **Не объединять движок грамматики с движком основного курса целиком.** У них разные модели прогресса.
  Достаточно общих частей: нормализация ответа, панель букв, сопоставление и сортировка.
- **Не менять идентификаторы ради красоты** (`26.a`, `24.1a`): на них держится прогресс.
