# План улучшений раздела «Грамматика»

Основание: [отчёт](AUDIT_REPORT.md), [архитектура](ARCHITECTURE_RECOMMENDATIONS.md),
[методика](PEDAGOGICAL_IMPROVEMENTS.md), [инструкции](GUIDELINE_IMPROVEMENTS.md).
Ничего из этого плана ещё не сделано: аудит ограничился документами.

## Как устроен план

- Работа идёт маленькими задачами. Каждая заканчивается зелёными проверками и не ломает прогресс
  учеников (не меняются `unit.id`, `group.id`, порядок вопросов и строки `answers`).
- Сначала то, что делает оценивание честным и даёт автоматический контроль. Потом — переработка юнитов:
  без линтера и новых правил те же дефекты появятся снова.
- Новые юниты можно продолжать добавлять параллельно, начиная с этапа 2 (после линтера и исправленных
  инструкций).

Объём: **S** — одна короткая задача; **M** — одна–две рабочие сессии; **L** — несколько сессий
или серия задач по юнитам.

## Этап 1. Схема данных и линтер содержания

Это основа для всего остального.

1. **Схема** `content/grammar/schema.json` по фактическим данным; проверка в `load_grammar()`;
   запрет неизвестных полей. Подробности — архитектура, п. 1.
2. **Строгие проверки загрузчика:** поля юнита, непустая инструкция мини-проверки (сначала как
   предупреждение: сейчас пустых 65), обязательный `theorySections`.
3. **Линтер** `python -m espanol grammar-lint [NN]` с правилами из архитектуры, п. 7, и файлом исключений
   `lint_allow.json`.
4. **Базовый замер:** запустить линтер по всем 45 юнитам и сохранить число предупреждений по юнитам
   в `docs/grammar_units/README.md`. Это точка отсчёта для этапа 4.

Готово, когда: все 45 юнитов проходят схему без правки данных; опечатка в имени поля роняет сборку;
линтер воспроизводит числа из приложения к отчёту (22 упражнения с преобладающим ответом, 120 шаблонных
пояснений, 79 сборок без лишних слов); в CI линтер запускается и не падает на существующих предупреждениях.

## Этап 2. Инструкции и справочник полей

1. Сгенерировать `docs/grammar_fields.md` из схемы; дописать примеры по каждому типу вопроса.
2. Заменить `content/grammar/AGENTS.md` текстом из [GUIDELINE_IMPROVEMENTS.md](GUIDELINE_IMPROVEMENTS.md), §3.
3. Внести правки гайда (§4 того же документа) и переименовать файлы.
4. Разделить `site_grammar_guide.md` на справочник и журнал; перенести 89 отчётов в архив; завести
   `docs/grammar_units/`.
5. Сократить абзац о грамматике в `CLAUDE.md`.

Готово, когда: в действующих инструкциях нет утверждений, противоречащих коду (проверка по списку
из отчёта, раздел 9); новый юнит можно написать, не открывая журнал изменений.

Проверка инструкций на деле — после этапа 3: дать двум моделям один небольшой юнит и сравнить результат.

## Этап 3. Честное оценивание

Три задачи, каждая с переносом существующих данных и своими тестами.

| № | Задача | Перенос данных | Готово, когда |
|---|---|---|---|
| 3.1 | Режим ударений `accents` в данных; убрать поиск слова «ударение» и список слов из логики | проставить режим всем юнитам так, чтобы поведение не изменилось; затем исправить несогласованные | тест: для каждого вопроса результат «без ударения» совпадает с прежним, кроме явно перечисленных изменений; сборка падает, если мягкий режим стоит на паре вида `tu / tú` |
| 3.2 | Нормализация пунктуации для ответов-предложений | 86 вопросов юнитов 39–45 получают `normalize: "phrase"`; лишние варианты остаются | фраза с точкой, без точки, с `¿ ?` и без — один результат; тест на 39.4 и 45.1 |
| 3.3 | Ответы по пропускам и разбор по каждому полю | 101 вопрос получает `gapAnswers`; строка `answers` сохраняется | в 38.1b#1 неверное поле подсвечено, рядом верное значение; жёлтый вариант работает для одного пропуска |

После 3.1 новые юниты о глагольных формах можно писать без риска, что `hablo` засчитается вместо `habló`.
**Это условие для продолжения курса в сторону времён.**

## Этап 4. Переработка практики юнитов 1–14

По одному юниту за задачу, по правилам обновлённого гайда. Теорию не трогаем, если нет ошибки.

**Порядок — от самых проблемных:** 7 → 5 → 13 → 8 → 2 → 14 → 3 → 1 → 11 → 10 → 9 → 4 → 6 → 12.

Что делается в каждом юните:

1. убрать варианты, которые никогда не верны, или добавить вопросы, где они верны;
2. переписать подписи, которые подсказывают решение;
3. разделить серии длиннее 15 вопросов; один вопрос — одно решение;
4. добавить контрастные случаи из теории и 2–3 разных действия на юнит;
5. переписать шаблонные пояснения;
6. проверить, что `theorySections` объясняет каждый вопрос.

Совместимость: изменённым группам увеличить `revision` (движок уже умеет начинать попытку заново);
`id` групп сохранить; при разделении упражнения новая часть получает новый `id`, старый результат остаётся.

Готово для юнита, когда: линтер даёт ноль необъяснённых предупреждений; браузерный проход на 320 и 390
без замечаний; отчёт `docs/grammar_units/NN.md`.

Юниты 18–45 в этот этап не входят: по ним достаточно пройтись линтером и исправить отдельные сигналы
(шаблонные пояснения в 22, 24–27, 36, 37; сборки без лишних слов).

## Этап 5. Мини-проверки и обратная связь

1. **Мини-проверки:** разрешить ввод; по всему курсу заменить вопросы с несуществующими словами
   и вопросы «достаточно одного из двух»; дать инструкцию каждой проверке. Объём большой (188 проверок),
   делать блоками тем.
2. **Пояснения к ожидаемым ошибкам** (`mistakes`, как в основном курсе) — сначала в юнитах с длинным
   вводом (25–27) и с местоимениями (35–39).
3. **Вторая попытка до показа ответа** — общая механика плеера.
4. **Исправление на вопросе-близнеце** (`retry`) — необязательное поле; заполнять по мере переработки юнитов.

Готово, когда: в работе над ошибками нельзя пройти вопрос, просто переписав показанный ответ, там,
где задан близнец; доля мини-проверок только из выбора заметно ниже 100 %.

## Этап 6. Скорость и хранение

1. Вынести тела юнитов и картинки заданий в отдельные файлы; в странице оставить каталог.
2. Попытки — отдельными ключами; черновик ввода — с задержкой; сообщение при ошибке записи;
   одноразовый перенос старого журнала.

Готово, когда: `index.html` меньше на объём грамматики (ориентир — минус 1,4 МБ текста и её картинки);
открытие юнита показывает загрузку и работает при повторном входе; тест переноса журнала с активной,
проваленной и завершённой попытками; запись на нажатие клавиши не зависит от числа пройденных юнитов.

Перед началом нужно решение автора об офлайн-работе (см. ниже).

## Этап 7. Новые форматы

1. Таблица типов вопросов в плеере (отрисовка, сбор ответа, разбор — по функции на тип).
2. Тип `match` (пары) и тип `sort` (по группам) на основе логики основного курса.
3. Первое применение — в юнитах, где формат естественен: 13 (меняется / не меняется по роду),
   44 (ситуация — `ser` или `estar`), 38 (кого / кому).

Готово, когда: оба типа описаны в схеме и справочнике, покрыты тестами оценивания и браузерным проходом
на ширине 320; одно неверное сопоставление — одна ошибка.

## Этап 8. Повторение и маршруты

1. Счётчики ошибок по вопросам в прогрессе (нужны для отбора).
2. Блок «Вспомни» в начале юнита: 3–4 вопроса из предыдущих.
3. Смешанная практика в конце блоков тем (артикли, местоимения, `ser / estar / tener`).
4. Рекомендуемые маршруты поверх номеров; пересмотр уровней.

Готово, когда: «Вспомни» собирается из существующих вопросов по `id` без дублирования содержания;
маршрут «С нуля» проходит от юнита к юниту кнопкой «Следующий урок».

## Этап 9. Тесты и уборка

1. Браузерный проход `tools/grammar_walk.mjs` в CI для изменённых юнитов.
2. Разделить `tests/site_grammar.test.cjs` по темам.
3. Заменить 30 снимков `grammar_before_unitNN.json` одним снимком подписей.
4. Удалить устаревшую форму `grammarForm` и её тесты.
5. Иконки юнитов — в данные.

Готово, когда: число тестов и покрытие сценариев не уменьшились; новый юнит не требует правки
`grammar_player.js`.

## Чего в плане нет намеренно

- Массовой переработки юнитов 18–45: они в порядке, им нужны точечные правки по линтеру.
- Перехода на фреймворк или сборщик.
- Изменения ритма «теория → практика».
- Изменения идентификаторов и сброса прогресса.

## Первый практический шаг

Если начинать завтра: **0.1 и 0.2** (час работы, убирают явные противоречия), затем **этап 1**
(схема и линтер). После него каждый следующий шаг можно проверять числом предупреждений, а не на глаз.
